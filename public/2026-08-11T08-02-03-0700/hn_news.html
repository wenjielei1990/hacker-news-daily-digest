France to ban unsolicited telemarketing calls HN 讨论 · 362

法国宣布从2026年8月11日起禁止未经请求的电话营销，旨在解决长期困扰民众的骚扰电话问题。由于推销电话泛滥，许多用户已养成不接陌生号码的习惯，导致重要通话常被漏掉。该禁令不仅影响法国国内，还对摩洛哥等国的呼叫中心产业构成巨大冲击，预计有数万个工作岗位面临风险。然而，法律的实际执行效果仍存疑，尤其是如何应对跨境诈骗和来电显示伪造技术。批评者指出，若无电信层面的技术拦截配合，单纯的法律条文可能难以彻底根除顽疾。

展开详情 ↓

法国政府正式出台禁令，严厉打击未经消费者同意的电话推销行为。这一政策背景是电信骚扰已严重破坏了电话网络的信誉，许多人为了躲避推销而拒绝接听所有未知来电，导致电话作为即时通讯工具的效用大打折扣。新规要求企业在拨打电话前必须获得明确授权，否则将面临高额罚款。这被视为保护公民隐私和恢复电话通讯正常功能的重要一步。

禁令的连锁反应已波及北非，特别是摩洛哥的呼叫中心行业。摩洛哥官员指出，该国约有4到5万个就业岗位依赖于法国的电话营销市场，法国市场的收入占比超过80%，禁令可能导致该行业面临灭顶之灾。这种跨国经济依赖性使得法国的消费者保护政策演变成了一场区域性的经济挑战。与此同时，合法企业可能会遵守规则，但那些游走在法律边缘的诈骗团伙是否会收敛仍是未知数。

许多技术专家对禁令的最终效果持保留意见，认为技术手段才是关键。目前的电信协议允许发件人伪造来电显示（Spoofing），使得追踪和拦截变得异常困难。虽然西班牙和瑞典等国已有类似的“罗宾逊名单”登记制度，但诈骗者往往通过境外拨号绕过监管。未来观察的重点在于法国是否会强制电信运营商采用更严格的身份验证协议（如STIR/SHAKEN），以及如何在全球化的电信网络中实现有效的跨境执法。

Rust SIMD on the GPU HN 讨论 · 102

VectorWare 宣布成功在 GPU 上实现了对 Rust 可移植 SIMD（core::simd）库的支持。该技术通过将 Rust 线程映射为 GPU 的 Warp，并将 SIMD 通道直接对应到 Warp 的硬件执行通道，使标准 Rust 向量代码能直接在 GPU 上运行。这种方法利用了 GPU 的 SIMT 架构，将元素级运算、掩码选择和跨通道洗牌等操作转换为原生的 GPU 指令。这意味着开发者可以编写一套代码，同时在 CPU 和 GPU 上实现高性能向量化运算。目前的主要限制在于性能高度依赖向量宽度与硬件 Warp 宽度的匹配，且该功能仍需 Rust Nightly 版本支持。

展开详情 ↓

VectorWare 的核心愿景是让 GPU 编程像普通 Rust 开发一样自然。继之前将 Rust 标准库和线程模型引入 GPU 后，他们现在实现了对 `core::simd` 的支持。在他们的模型中，一个 Rust 线程被映射为一个 GPU Warp，而 SIMD 向量的每个通道则对应 Warp 中的一个硬件执行单元。这种映射使得原本为 CPU 编写的向量化代码能够直接编译为 GPU 的 PTX 指令，实现了真正的代码级跨平台复用。

在实现细节上，简单的元素级算术运算被直接映射为 GPU 的原生指令。对于更复杂的跨通道操作，如 `reduce_sum` 或 `simd_swizzle`，VectorWare 利用了 GPU 的 Warp Shuffle（洗牌）指令来高效交换数据。此外，SIMD 掩码操作则通过 GPU 的投票（vote）和位图（ballot）指令完成。为了处理向量宽度与硬件不一致的情况，他们还开发了一套基于 Rust 类型系统的中间表示（IR），用于处理诸如“条带挖掘”（strip mining）等复杂逻辑，并提供了一个类似 Miri 的解释器进行确定性测试。

尽管前景广阔，该技术目前仍面临一些挑战。首先，`portable_simd` 在 Rust 中仍处于不稳定阶段，需要开启 Nightly 特性。其次，当 SIMD 宽度不等于硬件 Warp 宽度（如 NVIDIA 的 32）时，会导致硬件利用率下降或指令开销增加。此外，某些复杂的洗牌操作可能需要通过共享内存实现，从而产生额外的性能开销。VectorWare 表示，未来将探索自动向量化以及对张量核心（Tensor Cores）的支持，进一步模糊 CPU 与 GPU 编程的界限。

除非你深入了解现代 GPU 架构的细节，否则这并不显而易见。GPU 实际上并不是 SIMD，而是 SIMT（单指令多线程）。硅片层面看起来很像 SIMD，但编程模型不同。如果你去看 AMD 的 ISA 文档（它们是公开的），你会发现你没有像 x86 上 `__mm256` 寄存器那样的对应物。每个“线程”只处理单个标量值，如 int32 或 float32。然而，硬件会将 32 或 64 个运行相同程序的线程组合在一起运行。每个“线程”大致映射到一个 SIMD 通道。这种 SIMD 是隐式的，而不是显式的。主要区别在于“SIMD”执行对程序来说是某种程度透明的。你只需编写普通的标量代码，硬件模型就会高效地将其分发到 SIMD 执行单元。这并不完全是一种抽象，因为要榨取最大性能，你必须理解它的工作原理。你也可以在 CPU 上使用这种编程模型，Intel 的 ISPC 就做到了这一点。它是一种类似 C 的语言，具有类似于 GPU 着色器语言的执行语义，但可以编译为常规 CPU 代码，并将线程映射到 CPU 的 SIMD 通道上，就像 GPU 一样。

Smalltalk 非常有影响力且非常成功……不过，有一种更好的理解对象的方式。即，“对象”被定义为进程，“消息”是异步的，而 Smalltalk 的消息调用其实是间接函数调用。我知道你在想什么：“但没有哪种面向对象编程语言是这样工作的。你这样什么也理解不了。” 确实如此：这种建议的重构框架无法帮助你理解任何流行的面向对象语言，因为它们使用的是间接函数调用，而不是异步消息传递。Smalltalk 的间接函数调用并没有改变编程的语义。它仍然是数据结构和算法。如果你完全采纳 Alan Kay 的想法，你可以编写出文本中的单个字母可以自行排版的程序（正如 Kay 所描述的那样）。我主张这种编程模型在异步消息传递框架中能得到更准确的表达。Smalltalk 的函数调用确实有一个重要的好处，那就是“多义性”（polysemy）。我借用了这个词，用得可能不太准确。其好处是你可以定义非算法的思想。例如，你可以为 LOOKUP(key,table) 定义许多适用于多种数据结构的方法，现在你定义的不是一个配方，而是一个超越配方的思想。任何使用 LOOKUP 的配方 R 都会自动适用于 LOOKUP 支持的所有数据结构，即使 R 本身可能是针对其自身特定数据结构的特定配方。这是一个巨大的优势，值得利用面向对象特性来发挥。但即便如此，你仍然生活在算法和数据结构的世界里。多义性是一种语言特性，不会引起机械或范式上的改变。然而，异步消息传递确实改变了算法的设计方式，正如 Alan Kay 所预期的那样，也以一种直接的方式模拟了现实世界的实体。但大家已经都理解这一部分了。那么，为什么这是一种“更好”的对象思考方式呢？1) 它强调了多义性的优势，根据我的经验，面向对象教学往往会忽视这一点，尽管几乎所有人都在某种程度上为了这个目的而使用面向对象；2) 它解释了为什么面向对象程序仍然以算法和数据结构的形式组织；3) 它欢迎在同一个程序、函数甚至同一行代码中结合“对象”技术与算法及数据结构技术。它们是完全兼容的，在这个意义上，语言、库或数据库并不是非此即彼的“面向对象”或“非面向对象”。
