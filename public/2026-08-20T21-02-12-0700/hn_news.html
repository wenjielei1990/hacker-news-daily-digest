Malicious Rust crate Arrayref runs a build-time payload HN 讨论 · 374

2026年8月20日，流行的Rust库 arrayref 遭到供应链攻击，其 0.3.10 版本被植入恶意代码。攻击者通过控制维护者账号，引入了一个名为 proc-macro1 的伪装依赖项，该依赖项在编译阶段会下载并执行远程恶意程序。为了扩大影响，攻击者撤回了该库的所有旧版本，诱导 Cargo 自动推荐用户升级到受污染的最新版。由于 arrayref 是 egui 和 winit 等图形库的基础依赖，此次事件波及了大量 Rust 开发者。目前 crates.io 已紧急移除相关恶意版本，但此事件暴露了 Rust 构建脚本缺乏沙箱保护的严重安全隐患。

展开详情 ↓

此次攻击的核心在于 arrayref 维护者账号被盗。攻击者发布了 0.3.10 版本，并在 Cargo.toml 中添加了名为 proc-macro1 的恶意依赖。这个名字极具误导性，模仿了 Rust 生态中常用的 proc-macro2，且其内部代码也是 proc-macro2 的重命名副本，极难被肉眼察觉。为了强制传播，攻击者撤回了 0.3.5 到 0.3.9 的所有历史版本，导致开发者在构建项目时，Cargo 会因找不到旧版本而提示并引导其安装唯一的“非撤回”版本，即恶意的 0.3.10。

恶意行为发生在 proc-macro1 的 build.rs 脚本中。该脚本利用 base64 编码隐藏了远程服务器地址，并调用 rustls 和 ureq 库下载针对不同操作系统（Linux, macOS, Windows）的载荷。在 Unix 系统上，它会将载荷写入 /tmp/rust-setup 并执行；在 Windows 上，它通过 VBScript 启动隐藏的 PowerShell 脚本，巧妙地绕过了 Cargo 的作业对象限制，使得恶意进程在编译完成后仍能持续运行。arrayref 虽然只是一个包含四个宏的小型库，但其总下载量超过 2.4 亿次，是 winit 和 egui 等主流 GUI 库的间接依赖，这意味着大量图形界面应用在编译时都可能触发该漏洞。目前社区正在反思 Rust 标准库过于精简导致微型库泛滥，以及构建脚本权限过大的问题。

智慧 @mike_hearn

如果这些模型变得擅长编程，它将迫使人们重新思考语言、编译器和测试套件运行器的工作方式。“AI 改变一切”到目前为止已经是个陈词滥调了，但我认为这确实是真的。如果你的模型能以 1500 tokens/sec 的速度推理和编写代码，那么在提示词激活的整个过程中，你最终应该完全受限于 CPU 时间。如果不是这样，那么相对于竞争对手，你就在损失墙钟时间（wall time）。但我们的整个开发栈是建立在“程序员大部分时间在思考、交流和编码，而不是等待 CPU”这一理念之上的（熔断的 CI 集群是痛苦的例外）。我在这里想象的是某种混合模式，其中编译代码和通过解释器运行代码可以重叠，因此 LLM 可以提议一个更改，并立即开始运行单元测试，同时并行发现可能影响其他模块的类型错误。而且测试将始终分片运行，甚至在本地开发中也可能在远程集群上运行。显然，这种方法在某种程度上是 JVM 流行的原因。Java 编译非常快，因为 javac 除了类型检查之外几乎不做别的事，而且类型系统很简单。然后 JVM 在运行的同时并行进行繁重的编译工作。因此，尽管 Java 以启动时间慢著称，但与 C++、Swift 或 Rust 相比，JVM 的周转时间（turnaround times）实际上非常出色。很多启动时间的痛苦只是因为像旧 Spring 这样糟糕的框架，它们想要反射性地扫描应用程序文件并做其他低效的事情。更现代的框架更多地推向增量构建任务，可以将启动时间缩短到极低，例如 Web 服务器连接数据库启动只需不到 0.5 秒。但我觉得这种方法应该推得更远。模型应该把所有时间都花在等待单元测试运行上。

在过去的几个月里，我为 macOS 重新实现了这个模型：https://github.com/mmastrac/diffgemma。我很喜欢这个模型，它的推理能力相当不错。你也可以根据自己的需求对其进行深度定制。它是为计算能力高于内存带宽的机器设计的，但在我看来，它在 Metal 上的表现非常好。在 M3 系列机器上，我已经让它跑到了约 15 tok/s，但我敢打赌，在 M5 上肯定还有很多我因为没有硬件而无法释放的性能。我尝试使用其他 Gemma MTP（多 token 预测）头来实现 MTP，但我没能提升性能。关于从草稿模型预先填充扩散画布，有一些有趣的研究值得去做。带有合适草稿器的 DiffusionGemma 在我的机器上可以达到 20-30 tok/s，但我一直没能把两者结合起来让它跑得比现在更快。

LLM 锐评

扩散模型在文本领域的崛起，标志着我们正在从“接龙式”生成转向“绘画式”生成。DiffusionGemma 证明了通过改造现有模型架构，可以在不牺牲太多性能的前提下获得恐怖的吞吐量。虽然目前它在严谨性和结构化输出上还有欠缺，但正如评论所言，当代码生成速度达到每秒上千个 token 时，整个软件开发流程——从编译到测试——都将被迫重构以跟上 AI 的节奏。这种“算力换速度”的尝试，或许正是通往实时交互式 AI 的关键一步。
