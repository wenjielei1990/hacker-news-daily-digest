Shopify is moving from React Native back to Swift and Kotlin HN 讨论 · 581

Shopify 宣布将其移动应用架构从 React Native 重新转向原生开发（Swift 和 Kotlin）。该公司曾在 2020 年全面拥抱跨平台技术，但现在认为大语言模型（LLM）的进步彻底改变了开发成本的权衡。通过 AI 智能体，在两个平台上分别实现功能的成本已大幅降低，不再需要为了节省人力而牺牲原生性能。Shopify 开发了名为 Helix 的系统来辅助迁移，并计划逐步停止维护其知名的 React Native 开源库。这一转变标志着 AI 正在消除跨平台框架的核心优势，即“一份代码多端运行”的必要性。

展开详情 ↓

Shopify 决定放弃 React Native 并回归原生开发，其核心逻辑在于 AI 重新定义了软件开发的经济学。在 2020 年，Shopify 选择跨平台是为了避免“同样的功能写两次”带来的高昂成本，并让 Web 开发者也能参与移动端开发。然而到 2026 年，Shopify 发现 AI 智能体已经能够高效地完成代码翻译、测试和跨平台对齐工作，使得维护两套原生代码的负担显著减轻。原生开发的优势——更直接的平台功能访问、更少的中间层以及更好的性能——在成本降低后变得更具吸引力。

为了实现这一大规模迁移，Shopify 构建了名为 Helix 的系统，它将迁移过程拆解为可评审的小型“检查点”，并利用 AI 自动生成测试和代码。他们还通过解耦业务逻辑与 UI，实现了无需模拟器的“无头”测试环境，极大地加快了 AI 的反馈循环。目前，Shop 应用已在 12 周内完成了原生重构并上线，而拥有 300 多个屏幕的主应用 Shopify App 也在迁移中。尽管这一决策对 React Native 生态系统（如 FlashList 等库）造成了冲击，但 Shopify 认为，当 AI 能够处理重复性实现工作时，追求极致的原生体验才是未来的方向。

展开详情 ↓

YuE2 代表了 AI 音乐生成领域的一个重要转向，它通过“符号规划”（Symbolic Planning）解决了生成音乐往往缺乏结构感的问题。该模型不再仅仅依赖概率预测下一个音频采样点，而是先生成类似乐谱的符号表示，再将其转化为高质量音频。这种方法允许模型在创作过程中更好地处理旋律走向、和弦进行以及歌曲的段落划分。根据项目页面显示，YuE2 在与 SheetSage1 和 Madmom 等系统的对比中，在旋律捕捉和结构边界识别方面均取得了 SOTA（当前最佳）成绩。

《21世纪课堂乐理》是一本面向大学水平的免费开源在线教科书，旨在通过数字化手段教授音乐理论。它涵盖了从基础音高节奏到高级和声与曲式分析的完整课程，并利用 PreTeXt 系统实现了响应式网页设计。尽管冠以“21世纪”之名，其核心内容仍紧紧围绕西方古典音乐的传统调性理论。该资源的主要价值在于其开放获取的性质，降低了音乐教育的门槛。然而，它因未能充分涵盖爵士乐、流行乐及非西方音乐传统而受到部分读者的批评。

展开详情 ↓

这本项目是由普吉特海湾大学（University of Puget Sound）提供的在线教学资源，旨在为本科音乐理论课程提供一个现代化的数字平台。教科书内容分为多个部分，系统地引导学生学习五线谱记谱、音阶、和弦转位以及复杂的对位法。它采用了 PreTeXt 出版框架，使得教材可以在各种设备上流畅阅读，并配备了可搜索的索引和交互式练习。这种数字化的形式解决了传统纸质教材价格昂贵且更新缓慢的问题。

然而，深入观察其教学大纲可以发现，它在很大程度上延续了 18 世纪欧洲的音乐分析传统，例如继续使用数字低音（Figured Bass）和申克分析法（Schenkerian analysis）。虽然书中包含了一些嵌入式媒体链接，但其理论框架依然偏向于解释巴赫或贝多芬时代的音乐逻辑。对于希望学习现代音乐制作、音色设计或复杂节奏理论的学习者来说，这本教材可能显得有些守旧。未来的观察重点在于，这类开源项目是否会逐步吸收更多元化的音乐风格，以真正匹配其“21世纪”的标题。

PlanetScale 宣布推出 Neki，这是一个专为 PostgreSQL 设计的分布式分片解决方案。它允许用户将数据库扩展到多台机器上，同时在每个分片上保留原生的 Postgres 引擎，以确保对插件和标准 SQL 的完全兼容。Neki 通过一个智能路由层处理查询分发，并利用 JSON 格式的“数据拓扑”来管理数据分布。该系统支持在线扩容、无损架构变更和自动故障转移，旨在解决单机数据库在处理海量数据时的性能瓶颈。目前 Neki 处于平台预览阶段，且并非开源软件，这与该公司基于开源 Vitess 的背景形成了对比。

展开详情 ↓

Neki 是 PlanetScale 借鉴其在 MySQL 分片领域（Vitess）多年经验后，为 Postgres 打造的扩展方案。其架构由四个核心组件构成：Neki Router 负责解析 SQL 并生成分布式查询计划；每个分片运行标准的 Postgres 实例，确保了扩展、索引和性能表现与原生环境一致；Sidecar 进程则与数据库并存，优化了连接池管理；最后由控制平面协调在线重分片、版本升级和故障切换。这种设计让开发者可以继续使用现有的 ORM 和驱动程序，只需通过一个标准的连接字符串即可访问整个集群。

用户可以从单机模式起步，利用 Neki 提供的在线 DDL 和无损升级功能，待业务增长到单机极限时，再通过内置的工作流平滑迁移到分片架构。Neki 解决了大表维护困难、备份耗时长以及连接数限制等痛点，且无需像某些“兼容 Postgres”的分布式数据库那样牺牲特定的 SQL 特性或插件支持。然而，Neki 目前作为 PlanetScale 的托管服务推出，并未像 Vitess 那样开源，这在开发者社区中引发了关于厂商锁定和开源承诺的讨论。此外，作为预览版，它目前还不建议用于生产环境，且产品细节仍可能发生重大变化。

Proof of Capture: Apple Reference Image, but open source and using steganography HN 讨论 · 51

针对苹果最近推出的“参考图像”技术，开发者 María Benavente 发布了一个名为 Proof of Capture 的开源项目，旨在证明照片是由相机拍摄而非 AI 生成。该方案利用 Raspberry Pi 和 ATECC608 加密芯片，在拍摄瞬间为照片生成数字签名。与易丢失的 EXIF 元数据不同，它通过隐写术将签名直接嵌入像素中，使其在经过社交软件压缩后仍能保留。核心技术采用感知哈希（pHash），允许轻微的图像处理但能识别篡改。然而，该技术无法防御“屏幕攻击”，即拍摄一张显示 AI 图像的屏幕仍会被视为真实照片。

展开详情 ↓

Proof of Capture 是一个成本不到 100 美元的 DIY 相机项目，硬件核心是 Raspberry Pi Zero 和 ATECC608 安全芯片。其工作流程是：在快门按下时，系统计算图像的感知哈希（pHash），由芯片内的私钥进行签名，随后利用 DWT 和 DCT 频域隐写技术将签名嵌入图像像素。这种设计解决了传统数字签名在图像缩放或压缩（如 WhatsApp 传输）后失效的问题，因为签名信息与视觉特征紧密绑定。

相比苹果将信任根留在其私有云中的封闭做法，该项目强调开源和本地化验证。但这种方案也面临显著的权衡：为了兼容轻微编辑，pHash 牺牲了部分严谨性，导致约 15% 面积内的局部篡改可能无法被察觉，且目前尚不支持裁剪操作。此外，硬件层面的安全性也受到质疑，因为攻击者理论上可以绕过传感器，直接向加密芯片输入伪造的图像信号。尽管存在“模拟漏洞”（拍摄屏幕即可绕过验证），该项目仍为建立数字内容的真实性链条提供了一个可行的开源参考。

JEP 544: Ahead-of-Time Code Compilation HN 讨论 · 28

JEP 544 提议为 OpenJDK 引入提前（AOT）代码编译功能，旨在显著缩短 Java 应用的启动和预热时间。该机制通过在“训练运行”中将热点代码编译为原生机器码并存入 AOT 缓存，使应用在生产环境启动时能立即执行优化后的代码。与传统的静态编译不同，它保留了 JIT 编译的灵活性，允许 JVM 在负载变化时动态重新优化代码。测试显示，该技术可将流行框架的启动时间缩短 65% 到 80%。其主要限制在于 AOT 缓存与特定的 CPU 架构和垃圾回收器绑定，且需要开发者在构建流程中增加额外的训练步骤。

展开详情 ↓

JEP 544 是 Project Leyden 的核心组成部分，旨在解决 Java 长期以来的“预热”痛点。在传统的 HotSpot JVM 中，代码最初由解释器运行，随后通过 C1 和 C2 编译器逐步优化，这导致微服务或无服务器应用在启动初期性能较低。JEP 544 引入了一种混合模式：开发者先进行一次“训练运行”，JVM 会观察哪些方法是热点，并将其编译为原生代码存储在 AOT 缓存文件中。在后续的生产运行中，JVM 可以直接加载这些预编译的代码，跳过缓慢的解释和初始 JIT 编译阶段。

这种方案在性能和灵活性之间取得了平衡。由于它不是“闭世界”假设的静态编译，Java 的动态特性（如反射、动态类加载）依然完好无损。如果生产环境的负载特征与训练时不同，JIT 编译器仍能介入并生成更契合当前运行状况的代码。然而，这种便利是有代价的：AOT 代码对运行环境非常敏感，生产环境的 CPU 指令集（如 AVX-512）和垃圾回收器（GC）配置必须与训练环境完全一致，否则 AOT 缓存将失效。此外，由于 AOT 编译时无法预知某些静态字段的运行时确切值，其初始优化程度可能略低于经过长时间运行后的 JIT 代码。
