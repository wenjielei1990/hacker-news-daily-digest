Owed a billion dollars in Nvidia stock HN 讨论 · 100

1993年，Eric Gullichsen 作为 Nvidia 的早期技术顾问获得了 2.5 万股期权。合同明确规定期权在一年内全部归属，但 1996 年公司财务总监却按标准的四年归属期计算，仅允许他行权约 1.5 万股。随着 Nvidia 股价在随后三十年间暴涨并经历多次拆股，这笔被漏算的差额如今价值约 10 亿美元。Gullichsen 在 2024 年翻阅旧文件时才发现这一错误并聘请了律师，但 Nvidia 以诉讼时效已过为由拒绝和解。最终，由于“权利睡眠”时间太长，法律胜算渺茫，他选择放弃起诉，将此作为一段昂贵的教训。

展开详情 ↓

在 Nvidia 成立初期的 1993 年，Eric Gullichsen 受邀加入技术顾问委员会，并为 NV1 芯片贡献了关键的双二次纹理映射（biquadratic texture mapping）技术。作为回报，他获得了 2.5 万股期权，合同约定在一年内按季度完成归属。然而，当他在 1996 年移居汤加王国时，Nvidia 财务总监发函称其仅归属了 15,625 股（这恰好是四年归属期下十个季度的比例）。当时 Gullichsen 未加核实便行权并淡忘了此事。

直到 2024 年，在 Nvidia 成为全球市值最高公司的背景下，他重新翻阅原始合同才发现了这个严重的计算错误。经过累计 480 倍的拆股，当年缺失的 9,375 股期权如今已等同于 450 万股 Nvidia 股票，市值高达 10 亿美元。他聘请了顶尖律师与 Nvidia 交涉，对方律师虽然不否认合同条款的真实性，但坚称该主张已因超过诉讼时效而被禁止。这意味着即便合同确实被违反，法律也不再保护这种沉睡了三十年的权利。

最终，Gullichsen 意识到在法庭上很难通过撤销动议，决定不再进行无谓的法律缠斗。他以一种豁达的心态分享了这段往事，提醒创业者和顾问必须仔细核对每一份法律文件。这个故事不仅揭示了早期 3D 图形技术的竞争残酷性，也展示了在巨额财富面前，法律程序往往比合同正义更具决定性。

Fireworks AI 推出了名为 Ember-1 的新型推理模型，旨在解决当前大模型“想太多”导致的成本高昂问题。该模型基于 Kimi K3 构建，通过专门的训练学会了在保持答案质量的同时，减少约 40% 的推理 Token 消耗。这对于需要多轮对话的智能体任务尤为重要，因为冗长的推理过程在后续对话中会被反复计费。测试显示，它在医疗和编程等专业基准测试中达到了与原版相当的水平，甚至在性价比上超越了部分闭源旗舰模型。目前该模型仅作为研究预览版在 Fireworks 平台提供，且尚未公开模型权重。

展开详情 ↓

推理模型（如 Kimi K3）虽然逻辑强大，但往往将超过 90% 的 Token 消耗在内部思考过程（CoT）中。在多轮对话的智能体工作流中，这些冗长的推理痕迹会被反复读入上下文，导致成本呈平方级增长。Fireworks AI 发现，简单地通过参数调低推理强度会严重损害输出质量，因此他们开发了 Ember-1。通过 50 多次训练实验和 200 多次评估，他们教会了模型如何更高效地思考，在保留自我反思和纠错能力的同时，剔除了不必要的冗余推理步骤。

在 Bedside Bench 医疗测试和 SWE-bench 编程测试中，Ember-1 展现出了极高的性价比，其成本效益曲线在某些场景下优于 GPT-6 Astra 等模型。Fireworks 内部开发者在不知情的情况下切换到该模型，反馈显示其编码能力并未下降，实现了“无感”替换。然而，这种优化也面临现实挑战：虽然 Token 数量减少了，但如果服务商调高单价，用户的最终支出可能并不会显著下降。此外，作为基于 Kimi K3 的衍生模型，其核心能力上限仍受限于基础架构。

目前 Ember-1 已在 Fireworks 的 Serverless 平台上开启为期两周的研究预览。公司计划根据社区反馈决定是否将其转为永久服务，并打算推出更多针对特定行业优化的“Ember”系列模型。对于开发者而言，这标志着 AI 应用正从追求“通用巨型模型”转向追求“针对特定工作流优化的经济型推理模型”。

Go 语言使用代码托管地址（如 GitHub URL）作为包的命名空间，这导致代码与托管平台产生了强耦合。一旦项目需要从 GitHub 迁移到 GitLab 或其他平台，开发者必须修改所有相关的导入路径，这在大型项目中是一项巨大的工程。作者建议使用自定义域名（如 go.example.com）作为“虚荣域名”来解耦。通过在自定义域名下配置简单的 HTML 标签，可以引导 Go 工具链找到实际的代码仓库。这种做法虽然增加了灵活性，但也带来了维护域名的成本和域名过期被抢注的风险。

展开详情 ↓

Go 语言的去中心化包管理机制非常独特，它直接将代码的物理存放位置（例如 github.com/user/repo）作为包的唯一标识符。这种设计虽然省去了中心化仓库的麻烦，但却让代码深度绑定到了特定的托管商。如果一家公司决定从 GitHub 迁移到 GitLab 或自建服务器，他们将面临极其繁琐的重构工作：不仅要修改当前项目的所有 import 语句，还要处理所有依赖该项目的下游代码。作者提到，有些公司为了避免这种重构成本，甚至不得不长期同时支付多个托管平台的费用。

为了解决这个问题，作者提倡使用“虚荣域名”（Vanity URLs）。开发者可以利用 Nginx 或静态网页，通过 `<meta name="go-import" ...>` 标签将自定义域名指向实际的 Git 仓库。这样一来，即便后端托管地址发生变化，对外暴露的包名依然保持不变，实现了逻辑名称与物理位置的分离。然而，这种方案并非完美，它将风险从托管商转移到了域名所有权上。如果开发者忘记续费域名，或者域名注册商单方面采取行动，依赖该包的所有项目都会崩溃，甚至可能面临供应链攻击的风险。因此，在追求灵活性的同时，必须权衡长期维护域名的可靠性。

在暗网上自建网站的核心在于配置 Tor 的隐藏服务（Hidden Service）。作者通过修改 `torrc` 配置文件，将 Tor 生成的 .onion 地址映射到本地 Nginx 服务器的特定端口。由于 Tor 网络本身提供了端到端加密，服务器端无需配置传统的 TLS 证书或 HTTP/2 协议，Nginx 仅需监听本地回环地址即可。为了确保网站内的链接在暗网环境下正常工作，作者利用 Hugo 生成器的特性，专门为 .onion 域名构建了一套静态文件，解决了静态站点中常见的绝对路径跳转回明网域名的问题。

这种托管方式虽然提供了极高的匿名性和隐私保护，但也带来了显著的技术挑战。首先，Tor 网络的路由机制导致了极高的延迟，这使得传统的“多请求”网页加载缓慢，因此静态化和减少网络往返显得尤为重要。其次，.onion 地址是由 56 个字符组成的随机字符串，极难口头传播或记忆。此外，暗网环境并非永久稳定，Tor 协议的重大升级（如从 v2 迁移到 v3）曾导致大量旧地址失效。开发者在选择此方案时，必须在极致的隐私主权与用户访问体验、长期稳定性之间做出权衡。
